# Provenance: restaurant-ordering archetype visual reference board

- **Scope:** one illustrative JPEG for `restaurant-ordering`, an in-family training archetype (`tr-11` bakery ordering and the `fam-11` wood-fired pizzeria with its kitchen dashboard; one of the sixteen in `src/eval/prereg.mjs`) rather than one of the five evaluation families. It exists because the archetype's plan asserts a refusal state on the order path - an order cannot be placed with nothing in it (tr-11's zero total items, fam-11's empty cart) - and the board set for that state was empty (`mwg-train-ixp9`, per [`reference-board-gaps.md`](reference-board-gaps.md)). This record exists so nobody has to guess which side of the boundary it sits on: **A1, planning reference only** - not an evaluation target, not a training example, not generated-site evidence.
- **One board, not two:** the two families' assertions describe the same refusal. `reference-board-gaps.md` listed this archetype as needing both an empty and an error board; reading the plan, tr-11's "zero total loaves" and fam-11's "empty cart" are one state, so one board depicts it and the README records why there is no second.
- **Generation:** 2026-10-13 UTC, by `scripts/generate-archetype-boards.mjs --write --only restaurant-ordering`. The script passes `model: gemini-nano-banana-2.1` explicitly to the project's model gateway (`https://gemini.int.exe.xyz/v1beta/models/gemini-nano-banana-2.1:generateContent`, overridable with `MWG_TRAIN_IMAGE_ENDPOINT`) and fails closed unless the response's own `modelVersion` equals the requested model, so the board is gateway-attested `gemini-nano-banana-2.1`. Recorded settings: `responseModalities: ["IMAGE"]`, temperature 0.7, `maxOutputTokens` 8192; the board returned a 1376 × 768 JPEG. No seed was set, so the bytes are not reproducible from the prompt. The prompt is the one in the linked archetype README, and its exact UTF-8 digest is in the table below, so a regeneration can be proven to have used the same brief.
- **Rights:** [Google consumer-account terms](../accounts/google-antigravity-consumer.md) prohibit using AI-generated service content to develop machine-learning models. `excluded_from_training: true`; `approved_for_training: false`. No exclusive copyright, general image license, production or commercial reuse clearance is claimed, and no separate reuse/clearance document was supplied. Do not move this image into a corpus, an evaluation target, adapter or training work, or generated-site evidence. A visual review does not change that boundary.
- **Visual truth:** the bakery name, collection window, contact details, and every error string are invented, unverified placeholders. The JPEG does not demonstrate a working menu, cart, checkout guard, kitchen dashboard or server persistence, and it does not by itself satisfy the archetype's contract: the refusal behaviour is asserted by the plan and its verifiers, not by this picture.
- **Observed placeholder artefacts, inspected and accepted:** an independent vision review of this 2026-10-13 board (commissioned from a vision-capable model in a different family than the lane that produced it, which is text-only) returned ACCEPT. It quoted the alert "Your order could not be placed", the summary line "No items in your order yet", the inline message "Add at least one loaf or pastry before checking out" and the blocked-control note "Placing an order needs at least one item" exactly; confirmed the summary lists no items with Subtotal, Taxes and Total all at `$0.00` and the cart counter at `0` (coherence with the empty state); confirmed the Collection time and Contact details fields are filled with no error styling; and found no corrupted text. This record does not imply the board was clean beyond what that review quoted.
- **Coverage:** one board, for the empty-order refusal only. The menu, cart, receipt and kitchen-dashboard states are **not** pictured and must not be inferred from this image.
- **Where the state renders, and the comparator's scope boundary:** the refusal is a re-render of the checkout after a refused submission, so `board-states.json` maps this board to a deliberately null path with a source. As an interaction board it establishes the canonical visual reference under `kind: 'interaction'` with a null path, per the Wave 2 standard (booking `step4-error.jpg`; contact-lead, account-recovery and event-registration `step3-refusal`), and it is exempt from path-based comparator sweeps: `captureSignature` captures by URL, so reaching a refusal requires driving the refused submission, which is deferred to dynamic interaction capture in `check-cross-arm-parity` and is instrument work rather than a board task.
