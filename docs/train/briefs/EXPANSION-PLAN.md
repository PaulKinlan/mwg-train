# Broad web-app taxonomy and prompt matrix (planning specification)

**Status:** proposed, not generated or evaluated. This plan does not change the existing `tr-01`–`tr-30` corpus, the sealed evaluation briefs, the preregistration, or any acceptance count. It defines *new* independent training-side families for a future authoring pass. The current 15 training archetypes and 30 families are largely create-a-record forms with one-page harness journeys (`README.md`); relabelling those projects as games, blogs or SaaS would not supply the missing behaviours. The machine-readable companion is [`expansion-matrix.json`](expansion-matrix.json).

## Taxonomy: product intent, not a renamed form

The proposed archetypes below are **new behavioural categories**, not promises that the current scaffold supports them. Each needs an independently authored multi-step journey, visible state change and an observable assertion. `existing` means an approximate current training archetype exists; even then its current scaffold does not establish full-brief conformance. A surface (card, pricing tier or checkout page) is not necessarily a standalone application: model it as a composable surface linked to an actual conversion or state transition.

| Group | Archetypes and distinguishing acceptance journey | Existing nearest analogue |
| --- | --- | --- |
| Play and learning | **Browser game:** rules → play with keyboard/touch → win/lose → restart, score changes; **interactive explainer:** change an input → see a causally linked diagram/narrative update → reset; **interactive demo:** configure an API/tool example → run safely → inspect output/errors; **course/quiz:** lesson → answer → feedback → resume progress. | course-enrolment only (not course/quiz) |
| Reading and reference | **Editorial blog:** index/filter → read article → share/deep-link; **wiki/knowledge base:** search → cross-link → citation/history; **fan/community site:** browse canon/media → contribute or bookmark → moderation boundary; **documentation portal:** navigate/search/version switch → copy or run a self-contained example. | docs-site, community-forum (partial) |
| Commerce | **Storefront/catalogue:** browse/filter → variant selection → cart; **cart/checkout:** quantity/tax/shipping → *simulated* payment → durable receipt; **product card/comparison:** inspect details → compare/select → next step; **subscription/pricing tiers:** compare inclusions/limits → switch billing period → select tier → next step. | web-shop, restaurant-ordering (partial) |
| Business and identity | **B2B SaaS marketing/signup:** use-case → plan → company/workspace signup → onboarding; **sign-in/account recovery:** credentials/session → logout/login → safe recovery; **SaaS workspace:** permissioned member task → save → another member sees authorized result; **analytics dashboard:** filter range → inspect chart/table → save setting. | onboarding-auth, dashboard (partial) |
| Services and participation | **Booking:** availability → reserve → reload/cancel; **directory/listing:** search/filter → detail → submit or contact; **event/community:** discover → register → manage attendance; **support/helpdesk:** open ticket → reply/update state → verify history; **survey/eligibility:** answer branching questions → review → submit/result. | booking, directory-listing, event-registration, support-helpdesk, survey-form (partial) |

**Builder feasibility.** This is not an extension of the sealed five-archetype pilot table (`pilot/archetypes.mjs`). The 15 training archetypes live in `pilot/training-archetypes.mjs`; `pilot/frameworks.mjs` can currently emit a form, optional extra form, server list/detail/search, session and limited edit/steps. `src/eval/spec.mjs` closes route kinds and capability keys (`list_pages`, `detail_page`, `auth`). Existing training archetypes are **amber**: reusable primitives exist but their actual multi-page/role journeys are not generally driven. New blog/wiki/fan/game/explainer/demo/course/product-comparison/pricing/workspace categories are **red**: new rendering and browser-journey capability, and sometimes a new server state model, must be implemented and tested before they qualify as training pairs. Checkout and B2B signup are **amber-to-red**: a form/order or session primitive exists, but cart arithmetic, plan handoff, billing simulation and cross-role assertions are not thereby implemented. Do not add a new route kind or capability just to satisfy this document; propose a tested builder contract in a later bead, preserving byte identity of existing pilot and training trees.

**Boundary checks:** a fan site must be more than a generic blog if fandom navigation, contribution or moderation is the claim; a demo must actually execute or respond to changed inputs, not just display code; a pricing card alone is a surface and should be scored by selection and downstream flow, not static markup; login without server-owned sessions is not auth; checkout never transmits real payment credentials. Product cards belong in commerce briefs but also appear in directories and SaaS; tag their surface separately from the parent archetype.

## Multi-role prompt generation matrix

The axes are independent. The companion JSON defines group/archetype, scenario roles and required observable behaviours. A **role** here is a person with a job in the requested app, *not* a prompt-writing model persona. Separately, `wording_roles` in the JSON describe who narrates each of the two prompt variants; this changes wording only, not the structured specification. Each family names a primary actor and at least one distinct actor with a different permission or goal where relevant (buyer/seller; reader/editor; player/organizer; prospect/admin). Roles without privileged access (e.g. public game) can instead contrast first-time and returning users. Roles must change a journey or expected authorization state, not just the vocabulary in the prompt.

| Axis | Planned values | Guard against shortcut |
| --- | --- | --- |
| Product | 21 behavioural archetypes across 5 groups; optional surfaces `card`, `pricing`, `checkout`, `search`, `editor` | Record actual workflow, not surface-only screenshots. |
| Actor | Public visitor, returning user, purchaser, contributor/editor, workspace owner/admin, staff/operator; assign only applicable roles | Each declared role gets an interaction and permission/accessibility assertion. |
| Request mode | New generation; *separate* repair family with supplied original and independently verified defect | Never reuse a generation prompt as a repair example. |
| Context | Fictional topic × audience × locale × content length × device needs × framework × server/client architecture | Cluster split by topic/template/scaffold, not variants; no eval topic/copy reuse. |
| State | Stateless interaction; client transient; persisted public data; authenticated owner-scoped data | State level must follow the journey; do not require an artificial form for every archetype. |
| Guidance | 2–4 pinned applicable rule IDs plus required subset, only when demonstrated by the task | No generic “be accessible/modern” as a scored assertion; prove rule applicability. |
| Wording | Two genuinely distinct voices per family (e.g. commissioning owner and operational user), identical structured contract | Paraphrases stay in the same family/split. No role prompt may add or remove required properties. |

**Selection rule for the next authoring wave:** start with one independent family for each of the 21 archetypes (42 wording variants), then add a second family per archetype at a different topic/role/state combination (42 families, 84 variants total). This is a *target*, not a claim of ready data. Include a role pair on every family and a cross-role permission or handoff assertion wherever state changes hands. Balance groups and roles by counts of **families** rather than variants; never insist on a full Cartesian product of nonsensical combinations. Add a separate set of repair families only when a reproducible starting project and broken browser journey exist. Keep `tr-` namespace with new non-overlapping IDs allocated only after checking both manifests; IDs in the JSON are archetype IDs, not new brief IDs.

**Prompt authoring mechanism:** no prose prompt generator currently exists; `scripts/set-brief-schema.mjs` and `scripts/set-brief-flows.mjs` author schema/flow patches, not prose, and prompt text is not yet compiled into training examples. First write an authored family record and two independently reviewed prompt texts; only automate generation after a validator rejects any role-specific prompt contradicting the invariant routes, state or assertions. A future generator should take a canonical family object plus narrator role and seed, emit both prompts deterministically, store generator version/template/seed and near-duplicate cluster, and validate unchanged structured fields across variants. Do not mistake this JSON plan for an executable generator.

**Family assembly contract:** define primary and secondary roles, user-facing context, real content fixture, navigation/routes, state transitions, persistence, failure/empty/recovery path, applicable and required MWG rules, non-goals, and concrete browser assertions *before* writing either prose prompt. Draft v1 from an owner/commissioner voice and v2 from a day-to-day operator/user voice; validate both against exactly the same structured fields. Example for `pricing-tiers`: a prospect toggles monthly/yearly, compares included seats and chooses a tier; the workspace owner completes a sandbox signup and later sees the chosen plan. Assertions test displayed totals/limits after toggle, selection preserved into signup, and server-stored plan on reload. A static three-card render is a failure. Example for `browser-game`: a player starts, uses keyboard controls to change game state, reaches a terminal state and restarts; a returning player sees a score only if persistence was declared. A decorative canvas is a failure.

## Gates before any generation or training

1. Reserve family IDs and compare fingerprints of topic, scenario, user journeys, scaffold, prompt-template and target design against `docs/eval/briefs/manifest.jsonl` and `docs/train/briefs/manifest.jsonl`. Keep the sealed eval manifest unchanged; avoid direct copies of its briefs, target designs and themes. Hold an independent later test set for the new archetypes rather than evaluate on sibling training variants.
2. Validate each new brief against [`SCHEMA.md`](SCHEMA.md) and pinned `docs/eval/rules.json`. Do not alter the schema to make a missing flow appear supported. Existing `scripts/check-brief-schema.mjs`, route/served-route checks and disjointness gates remain necessary, not sufficient.
3. Prototype one representative from each group and verify all declared journeys in a real browser, including actual state transition, alternate-role access control where relevant, reload and failure recovery; capture before/after screenshots and trace/assertion results. Browser checks on generated projects are distinct from reviewing this planning document.
4. Separate corpus eligibility from brief acceptance: authored prompts are **not** training pairs; only provenance-cleared, runnable projects with independently checked uplift and preserved functionality may enter training. No real payments, secrets, private data, unlicensed fan assets or production auth providers.
5. Report coverage by archetype × role × state × rule with missing cells and rejection reasons. An unsupported archetype remains `planned` until its routes and multi-page journey are actually served and verified; do not silently fall back to the nearest booking/form template.

**Implementation sequence (not part of this bead):** author and validate new families; implement archetype-specific source builders or approved model generation; extend browser journeys for genuine multi-page/role state; run a small group-balanced pilot; only then scale accepted pairs and update preregistration via a documented deviation/new study if the sealed endpoint changes. No layouts or generated images are needed for the taxonomy specification; eventual generated products can request licensed/original imagery case by case.
