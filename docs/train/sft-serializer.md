# DeepSeek V4.1 Flash SFT serializer — offline and fail-closed

`src/train/serializer.mjs` transforms **explicitly approved** train-split manifest rows into one Fireworks-compatible JSONL chat sample per row: `{"messages":[{"role":"user","content":"<the exact pinned prompt>"},{"role":"assistant","content":"<the complete source tree>"}]}`. Fireworks requires OpenAI-compatible chat `messages` JSONL, 3–3,000,000 examples per dataset: [official SFT dataset format](https://docs.fireworks.ai/fine-tuning/supervised-fine-tuning), retrieved 2026-10-13, SHA-256 `cd8fd8673cfdf73d6330e9a8774b7ffaff17490d5d3a7a71e90e281042decef0`. This tool never uploads, trains, executes the generated code, or invokes a model. A single-pair local fixture is only a serializer test, **not a provider-eligible training dataset**.

## Row contract and output

Input is a JSONL manifest under `--root` with one row per project: `brief_id`, `family_id`, `split:"train"`, `project_id:"tr-NN-framework"`, `arm:"A1_self_generated"` (or another trainable arm), `excluded_from_training:false`, `approved_for_training:true`, nonblank `approved_by`, nonblank `approved_at`, `rights_ref` (an existing regular file beneath `--root`, not a symlink), `prompt_path`, `project_dir`, `prompt_sha256`, and `target_sha256`. The two SHA-256 values are `sha256:<lowercase hex>` over prompt **bytes** and the serialized source target **UTF-8 bytes** respectively. The manifest itself is hashed in the report. The provenance approval is a prerequisite, not inferred from corpus membership: current scripted corpus rows and training-target designs are **not** approved for training. These fields and a resolved rights file are still row assertions, **not** independent verification of the file's contents or the named approver; verify the provenance record separately before any training spend. The existing sealed evaluation-family/target-hash disjointness checker must pass on this exact input manifest. A malformed row, missing approval, changed bytes, symlink, unsafe path, or missing tokenizer aborts the *whole dataset* before any output is written.

The target sorts the application files by relative path; it excludes `node_modules`, `.git`, build directories (`dist`, `build`, `.next`, `out`, `coverage`, `_site`, `target`), lockfiles (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`/`bun.lockb` and `*.lock`), `README.md`, `.DS_Store`, and binary/font/image/map extensions. It omits only the **root-level** harness `spec.json`; a nested app `spec.json` remains source. Each file is represented as `FILE <JSON-escaped relative path> BYTES <UTF-8 byte length>\n<bytes>\nEND FILE\n`; the byte length makes a delimiter-like line in the source unambiguous. Source code remains inert data. Keep the framework named in the approved row/prompt, not another arm's scaffold. No images enter the student input or target; designs remain evaluation targets. An accepted dataset's report includes pair-level prompt/target/total measured tokens, distribution (minimum, p50, p95, maximum, total), manifest SHA-256 and the resulting dataset SHA-256 for the seam manifest. For precisely these same rows it also reports the `(prompt + target).length / 4` estimate and its percentage error versus tokenizer-measured totals; it does **not** mistake that comparison for the old full-corpus headline.

## Tokenizer and thinking policy

Count the *rendered full user+assistant conversation*, not `characters/4`, with `transformers==4.57.6` and the pinned `deepseek-ai/DeepSeek-V4.1-Flash` Hugging Face revision `2cba9e42aa026125f3ed06c6d98c1db82f7ca027`. Required files, obtained separately from that immutable revision (no model weights): `tokenizer.json`, SHA-256 `c90dfa01249db1be4245780a052ede752e1361c612ac6d08e2bdada7d599476b`; `chat_template.jinja`, SHA-256 `d959d804d5101b79a49b6ff1bf3c54cd5affa9a5a78c503d925f3090040b31c3`. `scripts/count-deepseek-sft.py` checks both hashes before accepting a dataset. It counts the exact rendered prompt prefix including the HF chat wrapper and generation prefix, then the entire conversation, verifying prefix token identity; no character estimate is admitted as a count. The result measures the **pinned HF template**, not an attested Fireworks server-side renderer: provider weight↔HF identity and training renderer are still unverified, so these numbers cannot alone authorize a managed training job.

The experiment uses the pinned high reasoning setting from [`decode-config.deepseek-flash.json`](../eval/decode-config.deepseek-flash.json) and [PREREGISTRATION §5](../eval/PREREGISTRATION.md). Render training counts in the HF template's `thinking_mode="thinking", reasoning_effort="high"`; targets contain final code only, with **no invented `reasoning_content` and no synthetic reasoning trace**. The pinned template emits empty `<think></think>` for such a target, not a fabricated chain of thought. Fireworks permits optional reasoning traces, but none were legitimately captured for this corpus; its [thinking-history policy](https://docs.fireworks.ai/fine-tuning/thinking-history) must not be treated as proof that an omitted trace preserves reasoning quality. The same pinned decoding, reasoning mode and total token budget must apply to C1/C2/C3/T. This may change the model's reasoning behaviour; evaluate explicitly before any owner-approved training or equal-budget model comparison.

The provider's [training-shape catalogue](https://docs.fireworks.ai/fine-tuning/models) (retrieved 2026-10-13; prior snapshot SHA-256 `f0f5af90afa8a1865530cfbedbbeb170a0954c4a9d0c4143d75a385d43adda7c`) lists the V4.1 LoRA shape `deepseek-v4p1-flash-262k-b300-lora` with **262,144** context, but the same model entry reports `trainCtx=65,536`. Until the provider resolves this discrepancy, the serializer reports both exceedance flags and refuses any row over the **smaller 65,536**, as well as over 262,144; it never truncates. Inference context, shape context and training context are distinct. V4 has a different revision and `trainCtx=131,072`; this V4.1 serializer must not be relabelled as V4.

## Local use (not training approval)

Install tokenizer tools into an external Python environment (`python3 -m pip install 'transformers==4.57.6'`; no dependency install from scratch in this worktree). Download the two exact-revision tokenizer files into one local directory and verify the hashes above. From the project root:

```sh
python3 scripts/count-deepseek-sft.py <pinned-tokenizer-dir> < input-messages-array.json
node scripts/check-disjoint.mjs --train <approved-manifest.jsonl>
mkdir -p .sft-output
node scripts/serialize-sft.mjs --manifest <approved-manifest.jsonl> --root "$PWD" --tokenizer-dir <pinned-tokenizer-dir> --output .sft-output/dataset.jsonl
```

`check-disjoint --train` checks the **input manifest**, not the produced chat JSONL. The serializer reruns that same disjointness gate on its exact input before producing any dataset; do not use the default `npm run check:disjoint` as proof about a custom manifest or output. The serializer command prints a report to stdout and writes the JSONL only on complete success; capture the report and its dataset SHA-256 in the seam manifest before any training planning. The existing `docs/train/corpus/tokens.json` figure of 2,764,257 is **derived** from target characters and omitted prompt characters; its relative error against an *approved matched-row dataset* cannot be stated until those rows exist. This is a sizing pipeline, not approval to incur spend. Provider checkpoint binding, entitlement, managed LoRA renderer and owner budget remain blocked elsewhere.
