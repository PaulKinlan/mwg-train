# Step 1a: evaluator interface decision (draft; Paul has not ratified it)

**Decision proposed:** A, a fixed, arm-independent interface contract appended by the future model-runner's prompt template, with B's accessible-name/role discovery only as an unambiguous browser-driving fallback. Do not edit the sealed brief text or claim this draft is an adopted preregistration change. Freeze the same template digest and decode request for C1, C2, C3, T, and the prompt half of training pairs *before* any run. No paid inference or training was made for this memo.

The interface contract must state the runtime shape (a runnable server entry point and storage persistence across reloads), create/record/update/search routes, field names, HTTP methods, ref extraction, the record-list/read endpoints and response shapes, and form control labels/roles or selectors. The harness should consume that same declared data, not assume `form#edit-form`, `/api/records`, `/api/record/<ref>`, `/api/me`, `#record-echo`, or `data-ref` without telling the model. `driveUpdateJourney` now accepts `spec.interface_contract.update` with `records`, `record` (a `{ref}` template), `current`, and optional `formSelector`; existing deterministic pilot projects retain their historical route defaults. When no form selector is supplied, the driver prefers a form with the named update field and an action button named Save/Update/Edit/Change, falls back to a unique form with that field, marks it temporarily, and refuses ambiguity. This decouples wrapper IDs; it does **not** remove the need to declare the API and the other journey paths for a generated project. A future runner must reject a missing interface contract for model-generated apps; `runProjectVersion` alone cannot tell a model-generated project from a pilot scaffold.

**Alternatives:** A alone is deterministic and reproducible but can reward complying with a prescribed API rather than unconstrained application design; undisclosed contract versions or arm-specific text bias the result. B alone tolerates independent HTML structures and promotes accessible controls, but duplicate labels, missing labels, divergent routes, and localStorage versus server persistence need predeclared failure rules. C (agentic/LLM judge) introduces a stochastic evaluator, model-dependent tool budget, and a moving decision boundary, contrary to §5's equal-evaluator rule. Use B only where the contract intentionally leaves a form wrapper ID free, fail closed on ambiguous matches, and keep success tied to reloaded UI plus persisted server state.

**Decode request proposal (not the historical request):** [`decode-config.deepseek-flash.json`](decode-config.deepseek-flash.json) records Fireworks model identity, `reasoning_effort=high`, `max_tokens=65536`, `top_p=1`, `stop=[]`, and intentionally omits temperature. The provider's [chat completion reference](https://docs.fireworks.ai/api-reference/post-chatcompletions) defines these request knobs; [Fireworks reasoning guide](https://docs.fireworks.ai/guides/reasoning) describes reasoning support. [DeepSeek's thinking-mode guide](https://api-docs.deepseek.com/guides/thinking_mode/) says temperature is ineffective in thinking mode and reasoning consumes the output budget. Docs retrieved 2026-10-13. Native DeepSeek behavior is **not** evidence that the Fireworks deployment implements it identically; before charging or comparing any arm, verify the pinned checkpoint, effective reasoning effort, provider acceptance of these parameters, usage breakdown, and finish reason. An unsupported setting blocks the run and requires a new config hash and approval; never silently substitute. `pinnedEvaluationBuildKey()` hashes the effective request alongside project and model without changing existing deterministic pilot keys. The future run record must store the entire request, its digest, endpoint, resolved model/checkpoint, response usage and finish reason for all arms. **Modern Web Guidance used:** the accessibility/forms guidance says “Prefer native naming mechanisms: `<label>` for form controls” and “Don't use `title` or `placeholder` as a naming mechanism.” I initially considered a broad selector over matching input names; the guidance supports semantic action labels, so the fallback now prefers a named update action, accepts a uniquely identifiable form when that name is unavailable, and fails on ambiguity instead of guessing a wrapper ID. This is a driver rule, not a claim that the recovered app itself meets accessibility requirements.
