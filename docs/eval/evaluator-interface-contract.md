**Decision adopted for tr-01:** A, a fixed, arm-independent interface contract appended by the model-runner's prompt template, with B's accessible-name/role discovery only as an unambiguous browser-driving fallback. The sealed briefs remain unchanged. Freeze the same template digest and decode request for default/C1/C2/C3/T, and before training for the prompt half of training pairs. No paid inference or training was made for the original memo.

The interface contract must state the runtime shape (a runnable server entry point and storage persistence across reloads), create/record/update/search routes, field names, HTTP methods, ref extraction, the record-list/read endpoints and response shapes, and form control labels/roles or selectors. It must also tell every arm that, after updating a record and reloading its record page, the stored new field value must appear in visible page text (`document.body.innerText`), not only as a prefilled edit input's `.value`. The update verdict independently requires a 200 record API response with the new field value, the old value gone, and an unchanged row count; persistence in the API without visible text on reload is a failure. The harness should consume that same declared data, not assume `form#edit-form`, `/api/records`, `/api/record/<ref>`, `/api/me`, `#record-echo`, or `data-ref` without telling the model. `driveUpdateJourney` now accepts `spec.interface_contract.update` with `records`, `record` (a `{ref}` template), `current`, and optional `formSelector`; existing deterministic pilot projects retain their historical route defaults. When no form selector is supplied, the driver prefers a form with the named update field and an action button named Save/Update/Edit/Change, falls back to a unique form with that field, marks it temporarily, and refuses ambiguity. This decouples wrapper IDs; it does **not** remove the need to declare the API and the other journey paths for a generated project. A future runner must reject a missing interface contract for model-generated apps; `runProjectVersion` alone cannot tell a model-generated project from a pilot scaffold.

**Alternatives:** A alone is deterministic and reproducible but can reward complying with a prescribed API rather than unconstrained application design; undisclosed contract versions or arm-specific text bias the result. B alone tolerates independent HTML structures and promotes accessible controls, but duplicate labels, missing labels, divergent routes, and localStorage versus server persistence need predeclared failure rules. C (agentic/LLM judge) introduces a stochastic evaluator, model-dependent tool budget, and a moving decision boundary, contrary to §5's equal-evaluator rule. Use B only where the contract intentionally leaves a form wrapper ID free, fail closed on ambiguous matches, and keep success tied to reloaded UI plus persisted server state.
