Visual design reference comparison

Each reference board from ../ beside the live page it informed, rendered in an iframe at a true 1280 × 900 desktop viewport and a 390 × 844 mobile viewport.

The boards are the two JPEGs committed alongside this demo. Per ../README.md they are "visual planning references only: not a working consultation form, a real submitted lead, a generated-site screenshot, a sealed evaluation target, or training/conformance evidence", and "the London address, identity, named attendee, email address, response-time promise, reference token and PDF button are unverified illustrated placeholders".

Nothing on this page is a screenshot: the right-hand frames are the live files in this directory, loaded in an iframe, so no capture is committed and none can drift from the implementation. The left-hand images are the boards themselves, unmodified.

1. Studio identity and the consultation form

Board ../step1-form.jpg (1376 × 768, SHA-256 da3e24a25265…) · live page index.html

Reference board

The board renders its own form with the browser chrome of the tool that captured it; it is a planning reference, not a capture of a working page.

Live page — 1280 × 900

Iframe viewport 1280 × 900, scaled to fit the column. Open it full size.

Live page — 390 × 844

Iframe viewport 390 × 844: the board's two columns become one, identity first.

  • Palette: page #0f172a with the board's faint drafting grid drawn as two CSS gradients, card surface #1e293b, action emerald #10b981, muted text #94a3b8 — the values the board's generation prompt names.
  • Layout: inside a 68rem frame the page is one column below 56rem and two from 56rem — identity on the left, form card on the right, as the board draws it.
  • Left column: the geometric studio mark, the identity line, the address block with its emerald pin icon, the four numbered process steps as an ordered list with one icon each, and the response-time pill. The board's step titles are uppercased by the stylesheet; their text is unchanged in the DOM.
  • Form card: the board's heading and its field order — Full Name, Work Email, Project Scope, Budget, Message — then the full-width Send Consultation Request action.
  • Character counter: the board's 0/500 characters is drawn from the textarea's own maxlength="500" and updated on every input event, so it counts what was actually typed rather than a number copied from the raster.
  • Budget control: the board's prompt names a "Budget range selector" but the board itself shows its Project Scope dropdown open across that part of the card, so the ranges are not visible in the raster. It is drawn here as a select of four ranges plus “Not sure yet”, in the same control style as the other fields, and marked optional.
  • Field labels: written in sentence case and not uppercased in CSS, so the visible label text ("Full Name", "Work Email", "Message") matches the DOM text exactly for anything reading the page.
  • Not on the board: the demo's own top bar and state switcher, which exist so this page and the success page can be reached from each other, and the note stating that submitting sends nothing anywhere.
  • Contrast deviation: the board draws a white label on the emerald button; white measures 2.54:1 there, so the demo keeps the board's emerald fill and uses a dark ink on it. The emerald itself is unchanged.

2. Submission acknowledgement

Board ../step2-success.jpg (1376 × 768, SHA-256 2afa857d88c5…) · live page success.html, seeded with the board's own sample values

Reference board

The board's own copy is model-generated placeholder text; only the acknowledgement pattern is adopted.

Live page — 1280 × 900

Iframe viewport 1280 × 900, scaled to fit. The frame is seeded with the board's sample name so the two can be compared; every value on it was typed into index.html and read back out of the URL. Open it full size.

Live page — 390 × 844

Iframe viewport 390 × 844, carrying a different submitted name and scope — the spec's own journey values — to show that the sentence and the panel follow what was typed rather than the board's raster.

  • Badge: the glowing emerald circle with a check sits over the card's top edge and is drawn in CSS plus one inline SVG. It carries the same dark ink as the primary action because white on #10b981 measures 2.54:1, below the 3:1 a graphical object needs.
  • Headline: Consultation Request Received, the board's wording, as the page's only h1.
  • Personalised line: the board's sentence with the name and email written into it. The live page reads ?name= and ?email= from its own query string and writes them as text with textContent — never injected as markup — because the enquirer controls both values.
  • Summary panel: the board's "Project scope" and "Reference token" rows on the raised surface, with the token in tabular figures. The panel is followed by a Your message block — the spec's echo container #enquiry-message has to show the message back, and board 2's panel does not have that row.
  • Scope echo: the board prints "Residential Renovation, Soho". The live page echoes the option the enquirer chose, without inventing a project location, so with the default selection it reads "Residential Renovation".
  • Reference token: #LEAD-7301 is the sample drawn on the board and is the same on every visit. The spec issues a real reference from the server's records table; nothing here does.
  • Buttons: Return to Home is a link to index.html styled as the primary action; Download Summary PDF is a real button that says in a live region that nothing is downloaded, because this directory generates no PDF.
  • Not on the board: the board's marketing chrome — "Step 2 · Successful contact consultation", Log in and Sign up — is replaced by the demo's own navigation, since this page is not a product's second step and has no accounts.
  • Sample state: opened with no query string at all, the page keeps the board's example values and says on the card that they are the board's illustrative example rather than a submitted enquiry.

Comparison page only. It asserts no match with the boards and no conformance result; the contract's server routes, its records table and its session are not implemented by this demo. Read README.md for what it does and does not do.
