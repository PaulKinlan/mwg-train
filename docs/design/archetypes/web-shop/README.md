The JPEG does not prove a working catalogue, cart, checkout guard or accessible alert; the empty-cart prevention behaviour is asserted by the brief and its verifiers, not by this picture.
- **Why this one state:** the brief's asserted states that a board can depict are the empty cart and the checkout refusal; of those, the corpus's parity and journey work names the empty cart (`tr-02`, [`plan.md`](plan.md):84). Error and payment states are **not** pictured and must not be inferred from this image.
- **Where the state renders, and why the mapping is null:** the generated arms for this archetype serve the pre-order **form** at `/` and the product **list** at `/products` (routes in [`pilot/training-archetypes.mjs`](../../../../pilot/training-archetypes.mjs)); there is no cart route and no empty-basket page. The empty basket is therefore a state of the shopping flow, not a document, and `board-states.json` registers this board as `kind: interaction` with a deliberately null path - the same convention as the Wave 2 refusal boards and booking's `step4-error.jpg`. Comparing it against the blank order form at `/` would measure an empty-basket design against a form, which is why it is not mapped there (mwg-train-wrsj). If the corpus should serve an empty-cart state, that is a change to the training archetype's routes, not to this board. **Scope boundary:** as an interaction board it establishes the canonical visual reference under `kind: 'interaction'` with a null path, per the Wave 2 standard (booking `step4-error.jpg`; contact-lead, account-recovery and event-registration `step3-refusal`), and it is exempt from path-based comparator sweeps: `captureSignature` captures by URL, so reaching a refusal or an empty flow state requires driving the interaction, which is deferred to dynamic interaction capture in `check-cross-arm-parity` and is instrument work rather than a board task.
